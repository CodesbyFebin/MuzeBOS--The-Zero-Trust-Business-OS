## Architecture

### Execution Substrate

MeTaBos runs on **Kubernetes Agent Sandbox** (`agents.x-k8s.io/v1beta1`),
a SIG Apps CRD purpose-built for stateful, singleton AI agent workloads.
Each worker agent is a `Sandbox` — a single pod with stable hostname,
persistent storage, and lifecycle control (create, pause, resume, delete).

| Layer                | Technology                                                     |
|----------------------|----------------------------------------------------------------|
| Backend              | FastAPI, SQLAlchemy, Alembic, PostgreSQL, Redis                 |
| Agent orchestration  | `grok-4.20-multi-agent` swarm leaders, Temporal workflows,     |
|                      | governed planning services                                     |
| Worker execution     | Kubernetes Agent Sandbox CRD (`Sandbox`), 5–10 `SandboxTemplate`|
|                      | per swarm, `SandboxWarmPool` for sub-second claim              |
| Isolation            | Kata Containers (Firecracker VMM) for code-exec workers,       |
|                      | gVisor for research/tooling workers, runc for API-only workers |
| Memory               | PostgreSQL, Qdrant, structured memory protocol, operation graph|
| System of record     | ERPNext plus PostgreSQL                                         |
| Frontend             | Next.js, React, Tailwind CSS                                    |
| Governance           | Owner JWT auth, OPA authorization, approval records, audit     |
| Observability        | /health, /ready, /metrics, Prometheus/Grafana                   |
| Deployment           | Docker Compose (dev), K8s + Caddy edge (prod), backup/restore  |
| Interoperability     | MCP-style tool contracts, A2A-style agent interop              |

### Swarm Topology

- **20 swarm leaders** (Grok 4.20 multi-agent), one per namespace
- **50 workers per swarm** (1,000 total), heterogeneous roles from 2 categories
- **5–10 SandboxTemplates per swarm** grouped by isolation × resource × egress
- **SandboxWarmPool** per template: 20% pre-warmed (10 per swarm)
- **No inter-swarm traffic** — cross-swarm coordination via MeTaBos control plane only

### Template Grouping Strategy

Workers within a swarm are **heterogeneous** (mixed roles from 2 categories)
but share **5–10 execution profiles**:

| Profile | Isolation | Resources | Egress | Used by (Swarm 01 example) |
|---------|-----------|-----------|--------|---------------------------|
| `code-exec` | kata-fc | 1 vCPU / 1 GiB | npm, PyPI, GitHub:443 | AI SWE, CI, code review |
| `code-light` | gvisor | 500m / 512 Mi | PyPI:443, API:443 | QA, lint, test runners |
| `research` | gvisor | 500m / 512 Mi | broad 443 (no metadata IP) | IT research, doc search |
| `api-light` | runc | 250m / 256 Mi | MeTaBos API:8443 only | Helpdesk, monitoring, ticket ops |
| `writing` | runc | 250m / 256 Mi | xAI API:443, storage:443 | Runbook writer, doc generator |

Decision	Rationale
5 templates, not 50	Templates encode execution shape (isolation, CPU, egress), not role. Role is injected at claim time.
Kata-fc only for code-exec	Workers that run LLM-generated code get VM isolation. The other 4 profiles run trusted tooling → gVisor or runc is sufficient and cheaper.

api-light has no external egress	Helpdesk/monitoring workers only talk to the MeTaBos control plane. Zero internet exposure.
Metadata IP blocked everywhere	169.254.169.254/32 excluded from all egress — prevents cloud credential theft via SSRF.
ttlSecondsAfterClaimed	Workers auto-expire. No zombie sandboxes. Temporal workflow re-claims or releases.

14. Key Design Decisions (Summary)
Decision	Rationale
5 templates per swarm, not 25	Templates encode execution shape, not role. Role injected at claim.
Kata-fc only for code-exec	Workers running LLM-generated code get VM isolation. Others use gVisor/runc.
Shared vLLM pool for workers	500 workers don't each need a GPU. 16 H100s serve all 500.
Dedicated leader inference	Leaders need 262K context + low latency. Can't share with workers.
No inter-swarm traffic	Blast radius containment. Cross-swarm via control plane only.
Metadata IP blocked everywhere	Prevents cloud credential theft via SSRF.
AWQ for worker pool, FP8 for leaders	Workers: throughput matters (AWQ = 1 GPU). Leaders: context + quality (FP8 = 2 GPU).
Temporal for workflows	Durable execution survives pod crashes. Approval signals are native.
Llama 4 Agent Framework	Apache 2.0, hierarchical patterns match topology, no vendor lock.

Researched MCP ecosystem and agent architectures
MeTaBos — 500 Self-Evolving AI Employees (Blueprint Section 15)
Open-source, self-hosted, MCP-connected, human-approved. Each employee lives in its own sandbox, learns from peers, and evolves to mastery.

15.1 Design Principles
Principle	Implementation
Open-source only	Every agent is a Llama 4 Scout/Maverick instance running on the shared vLLM pool. No proprietary model calls.
Self-evolving	Each agent has a Skill Memory (persistent, per-role) that grows via: (a) task completion reflection, (b) peer skill transfer, (c) observer critique feedback. Inspired by Hermes Agent's learning loop + OpenSkill's open-world skill acquisition.
Dedicated sandbox	1 agent = 1 Sandbox CRD. No sharing. Full isolation.
MCP-native	Every agent connects to the outside world exclusively via MCP servers (15,930+ public servers available).  No custom glue code.
Human approval gate	ALL outgoing actions (external API calls, emails, payments, deployments, legal filings) require owner approval via the Next.js console before execution. Internal actions (memory writes, internal queries, skill updates) are autonomous below impact threshold.
Peer learning	Agents in the same swarm share a Skill Exchange (Qdrant collection per swarm). When Agent A masters a sub-task, its skill is published. Agent B in the same role can pull it.
Mastery progression	Each agent has a Skill Level (1–10) per sub-capability. Level advances only when: (a) task success rate >90% over 50 tasks, (b) Observer Agent validates no drift, (c) skill is peer-reviewed by 2+ same-role agents.

15.4 MCP Architecture (Central Gateway)
~15,930 public MCP servers available (official registry: registry.modelcontextprotocol.io).  MeTaBos uses a central MCP Gateway (self-hosted) that all 500 agents connect through.

Why a Gateway (not direct connections)
Concern	Solution
Auth	Gateway holds OAuth2/OIDC tokens; agents get scoped, per-task, expiring credentials
Approval gate	ALL outgoing MCP calls pass through the gateway → approval check → execute or reject
Audit	Every tool call logged with agent ID, timestamp, parameters, result
Rate limiting	Per-agent, per-swarm, per-tool quotas
FOSS policy	Gateway enforces: no data-sharing, no hosted-service dependency without declaration
Discovery	Agents query the gateway for available tools matching their role

15.6 Human Approval (JEV Gate) — All Outgoing Actions
"JEV" = Just-in-time External Validation. Every action that touches the outside world requires owner approval.

Approval Matrix
Action Class	Examples	Approval	TTL
Internal (autonomous)	Memory write, skill update, internal query, peer skill pull	None	—
Internal-high (logged, no gate)	Create new role, modify workflow, update KPI	Observer review (async)	—
External-low (auto-approve with log)	Read-only API call, fetch data, search	None (logged)	—
External-medium (owner approval)	Send email, create CRM record, post to social, schedule meeting	JEV: owner clicks approve	30 min
External-high (owner + Observer)	Send payment, sign contract, deploy to prod, file legal, terminate employee	JEV: owner + Observer Agent both approve	15 min
External-critical (owner + 2-person)	>$10K spend, legal filing, data deletion, security credential change	JEV: owner + second human (configurable)	10 min

Approval Record Schema (PostgreSQL)
CREATE TABLE approvals (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    agent_id      UUID NOT NULL,          -- which sandbox requested
    swarm_id      TEXT NOT NULL,
    action_class  TEXT NOT NULL,          -- internal / external-low / medium / high / critical
    tool_name     TEXT NOT NULL,          -- MCP tool (e.g., "gmail.send")
    parameters    JSONB NOT NULL,         -- full tool call params
    impact_score  NUMERIC(2,1) NOT NULL,  -- 0-10
    status        TEXT DEFAULT 'pending', -- pending / approved / rejected / expired
    approved_by   UUID,                   -- owner JWT sub
    observer_ok   BOOLEAN,                -- Observer Agent validated
    created_at    TIMESTAMPTZ DEFAULT now(),
    expires_at    TIMESTAMPTZ NOT NULL,   -- TTL from action_class
    resolved_at   TIMESTAMPTZ,
    audit_hash    TEXT NOT NULL           -- hash chain: H(prev_hash || this_record)
);

Cross-Swarm Learning (controlled)
Mechanism	How
Swarm-to-swarm	COA identifies a skill in Swarm 01 that would benefit Swarm 05. Creates a "skill transfer" approval. Owner approves. Skill is copied to Swarm 05's collection with attribution.
Role-specific global	All "AI Bookkeeper" agents across all swarms share a global-finance-skills collection. When one masters a new reconciliation pattern, all benefit.
Failure sharing	When an agent fails, the failure mode is published (anonymized) to the swarm's failure-modes collection. Other agents learn what NOT to do.

Mastery Progression
Level 1:  New agent. Base skill from role template. 0 tasks done.
Level 2:  10 tasks completed, >70% success.
Level 3:  25 tasks, >80% success. First peer skill pulled.
Level 4:  50 tasks, >85% success. Observer validated.
Level 5:  100 tasks, >88% success. Can teach (skill published).
Level 6:  200 tasks, >90% success. Handles edge cases.
Level 7:  350 tasks, >92% success. Peer-reviewed by 3+ agents.
Level 8:  500 tasks, >94% success. Observer: "mastery confirmed."
Level 9:  750 tasks, >96% success. Creates new sub-skills.
Level 10: 1000+ tasks, >97% success. "Master." Can mentor new agents.

Level gates are enforced by the COA. An agent at Level 3 cannot be assigned Level 7 tasks. The COA routes by mastery level.

15.9 Sandbox Configuration (per agent)
Each of the 500 agents gets its own dedicated sandbox (not shared). The 5 SandboxTemplate profiles per swarm determine the execution shape; the agent identity is injected at claim time.

Per-Agent Persistent Storage
# Each sandbox has 3 volumes:
volumeClaimTemplates:
- name: workspace          # Task files, code, temp (1 GiB)
- name: skill-memory       # Persistent skill files (512 Mi, NEVER deleted)
- name: trajectories       # Last 100 task traces (256 Mi, rolling)

skill-memory is the key volume. It persists across sandbox restarts. When an agent is released and re-claimed, its skills are intact. This is what makes "self-evolving" real — the agent doesn't reset.

NetworkPolicy (per sandbox — strict)
egress:
# 1. vLLM inference (LLM calls)
- to:
  - namespaceSelector: {matchLabels: {name: inference}}
  ports: [{protocol: TCP, port: 8000}]

# 2. MCP Gateway (ALL external tool calls go through here)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 9000}]   # MCP Gateway

# 3. Control plane API (task state, approvals, memory)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 8443}]   # FastAPI

# 4. Qdrant (skill exchange, retrieval memory)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 6333}]

# NO direct external egress. Period.
# All external calls MUST go through MCP Gateway → approval → execute.

This is the critical security property: an agent in a sandbox cannot make a direct HTTP call to Gmail, GitHub, or any external API. It MUST go through the MCP Gateway, which enforces the JEV approval gate.

                "task_context": task.context
            }
        )
        if r.status_code >= 400:
            raise HTTPException(500, f"Sandbox claim failed: {r.text}")

    # 4. Mark worker busy
    worker["status"] = "in_progress"
    worker["current_task"] = task.task_id

    async with TemporalClient.connect(app.state.temporal) as tc:

        )

    """Worker (or Temporal workflow) reports completion."""
    # Find which agent had this task
    agent_id = None
    for aid, w in app.state.workers.items():
        if w["current_task"] == task_id:
            agent_id = aid
            break

    if not agent_id:
        raise HTTPException(404, "Task not found")

    w = app.state.workers[agent_id]
    w["status"] = "idle"
    w["current_task"] = None
    w["tasks_completed"] += 1

    # Update success rate (exponential moving average)
    alpha = 0.1
    w["success_rate"] = alpha * (1.0 if success else 0.0) + (1 - alpha) * w["success_rate"]

    # Mastery progression
    if w["success_rate"] > 0.9 and w["tasks_completed"] % 50 == 0:
        if w["mastery"] < 10:
            w["mastery"] += 1
            log.info("mastery_up", agent=agent_id, level=w["mastery"])

    # Skill publication
    if skill_extracted and success:
        await publish_skill(agent_id, task_id)

    # Release sandbox
    async with httpx.AsyncClient() as client:
        await client.post(
            f"{app.state.control_plane}/api/sandbox-claims/{agent_id}/release"
        )

    return {"status": "completed", "agent": agent_id, "success": success}

Architecture
Agent sandbox

    │  MCP tool call: {tool: "gmail.send", params: {...}}
    ▼
┌─────────────────────────────────────────────────────────────────┐
│  JEV GUARD SERVICE (FastAPI, 3 replicas)                         │
│                                                                   │
│  1. AUTH: Verify agent JWT (scoped, per-task, expiring)          │
│  2. POLICY: OPA check — is this tool allowed for this role?      │
│  3. CLASSIFY: Internal vs External (from MCP config)             │
│  4. PII SCAN: Presidio NER on all string params                  │
│  5. POLICY MEMORY: Qdrant check — does this match a              │
│     previously-rejected pattern? (learned from past rejections)  │
│  6. IMPACT SCORE: LLM-lite call (8B model) for scoring           │
│  7. ROUTE:                                                       │
│     - internal → EXECUTE immediately                             │
│     - external-low → EXECUTE + log                               │
│     - external-medium → CREATE APPROVAL → wait for owner         │
│     - external-high → CREATE APPROVAL + Observer validation      │
│     - external-critical → CREATE APPROVAL + 2-person rule        │
│  8. AUDIT: Hash-chained log entry (always)                       │
│  9. EXECUTE or QUEUE: Call MCP server or hold in approval queue  │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
    │
    ├── (approved) → MCP Server → External system
    └── (rejected/expired) → Agent notified "blocked"

async def verify_agent_token(
    credentials: HTTPAuthorizationCredentials = Depends(security)
) -> dict:
    """Verify the agent's scoped JWT. Token is issued at sandbox claim time."""
    import jwt
    try:
        payload = jwt.decode(
            credentials.credentials,
            config.JWT_SECRET,
            algorithms=["HS256"]

        if payload.get("exp", 0) < time.time():

# ─── PII SCAN (Presidio) ──────────────────────────────────────────────────────
def scan_pii(text: str) -> list[PiiFinding]:
    """Run Presidio NER on text. Returns findings with recommended action."""
    analyzer = get_analyzer()
    results = analyzer.analyze(
        text=text,
        language="en",
        return_explanation=True
    )
    findings = []
    for r in results:
        # Determine action based on entity type
        if r.entity_type in ("CREDIT_CARD", "PAN", "IP_ADDRESS", "MAC_ADDRESS"):
            action = "block"  # These should NEVER be in outgoing params
        elif r.entity_type in ("PERSON", "EMAIL_ADDRESS", "PHONE_NUMBER", "PASSPORT_NUMBER"):
            action = "flag"   # Flag for approval, don't auto-block
        elif r.entity_type in ("MEDICAL", "FINANCIAL_ACCOUNT"):
            action = "block"
        else:
            action = "flag"

        findings.append(PiiFinding(
            entity_type=r.entity_type,
            score=r.score,
            start=r.start,
            end=r.end,
            text=text[r.start:r.end],
            action=action
        ))
    return findings

def scan_all_params(params: dict) -> list[PiiFinding]:
    """Recursively scan all string values in params for PII."""
    all_findings = []
    def _walk(obj, path=""):
        if isinstance(obj, str):
            findings = scan_pii(obj)
            for f in findings:
                f.entity_type = f"{f.entity_type} (at {path})"
            all_findings.extend(findings)
        elif isinstance(obj, dict):
            for k, v in obj.items():
                _walk(v, f"{path}.{k}")
        elif isinstance(obj, list):
            for i, v in enumerate(obj):
                _walk(v, f"{path}[{i}]")
    _walk(params)
    return all_findings

# ─── QDRANT POLICY CHECK (learned rejections) ─────────────────────────────────
async def check_policy_memory(tool_name: str, parameters: dict) -> Optional[str]:
    """
    Check Qdrant for previously-rejected patterns.
    If this call matches a past rejection (high similarity), auto-block.
    This is the 'learning from rejections' mechanism.
    """
    qdrant = get_qdrant()

    # Create a simple embedding of the tool call (use hash-based for speed)
    # In production, use the 8B model for semantic embedding
    call_signature = f"{tool_name}:{json.dumps(parameters, sort_keys=True)[:500]}"
    # Simple: use first 384 chars as a pseudo-vector (replace with real embedding in prod)
    pseudo_embedding = [ord(c) % 256 / 255.0 for c in call_signature[:384].ljust(384)]

    try:
        results = qdrant.search(
            collection_name=config.QDRANT_REJECTION_COLLECTION,
            query_vector=pseudo_embedding,
            limit=3,
            score_threshold=0.92,  # Very high similarity = likely same pattern
            filter=Filter(
                must=[
                    FieldCondition(key="tool_name", match=MatchValue(value=tool_name))
                ]
            )
        )
        if results:
            top = results[0]
            return (
                f"Matches previously-rejected pattern (score={top.score:.3f}). "
                f"Original rejection: {top.payload.get('reason', 'N/A')} "
                f"by {top.payload.get('rejected_by', 'owner')} "
                f"at {top.payload.get('timestamp', 'unknown')}"
            )
    except Exception as e:
        log.warning("qdrant_policy_check_failed", error=str(e))

    return None

# ─── IMPACT SCORING (8B model) ────────────────────────────────────────────────
async def score_impact(tool_name: str, parameters: dict, context: dict) -> ImpactScore:
    """Use the 8B model to score impact of this action (0-10)."""
    prompt = f"""Score the impact of this business action on a scale of 0-10.
0 = trivial internal read
10 = irreversible, high-cost, external, or legally binding

Action: {tool_name}
Parameters: {json.dumps(parameters)[:2000]}
Context: {json.dumps(context)[:1000]}

Respond with JSON: {{"score": <0-10>, "reasoning": "<one sentence>", "risk_factors": ["..."]}}"""

    try:
        async with httpx.AsyncClient() as client:
            r = await client.post(
                f"{config.LITE_LLM_ENDPOINT}/chat/completions",
                json={
                    "model": "meta-llama/Llama-3.1-8B-Instruct",
                    "messages": [{"role": "user", "content": prompt}],
                    "temperature": 0,
                    "max_tokens": 200
                },
                timeout=10
            )
            if r.status_code == 200:
                text = r.json()["choices"][0]["message"]["content"]
                # Extract JSON from response
                import re
                match = re.search(r'\{.*\}', text, re.DOTALL)
                if match:
                    data = json.loads(match.group())
                    return ImpactScore(
                        score=float(data.get("score", 5)),
                        reasoning=data.get("reasoning", ""),
                        risk_factors=data.get("risk_factors", [])
                    )
    except Exception as e:
        log.warning("impact_scoring_failed", error=str(e))

    # Fallback: rule-based
    return _rule_based_score(tool_name, parameters)

def _rule_based_score(tool_name: str, parameters: dict) -> ImpactScore:
    """Fallback scoring if 8B model unavailable."""
    score = 3.0
    factors = []

    # Read-only tools are low impact
    if any(v in tool_name for v in ("get", "list", "search", "read", "fetch")):
        score = 1.0
    # Write tools are medium
    elif any(v in tool_name for v in ("create", "update", "send", "post")):
        score = 5.0
        factors.append("write_operation")
    # Destructive tools are high
    elif any(v in tool_name for v in ("delete", "terminate", "revoke", "block", "file")):
        score = 8.0
        factors.append("destructive_operation")
    # Financial operations
    if any(v in str(parameters).lower() for v in ("amount", "price", "payment", "invoice", "transfer")):
        score = max(score, 7.0)
        factors.append("financial")
    # Legal operations
    if any(v in tool_name for v in ("sign", "file", "contract", "legal")):
        score = max(score, 8.0)
        factors.append("legal")
    # Security operations
    if any(v in tool_name for v in ("block", "revoke", "disable", "ban")):
        score = max(score, 7.0)
        factors.append("security")

    return ImpactScore(score=score, reasoning="Rule-based fallback", risk_factors=factors)

# ─── DETERMINE ACTION CLASS ───────────────────────────────────────────────────
def determine_action_class(tool_name: str, server_id: str, impact: ImpactScore, pii: list[PiiFinding]) -> ActionClass:
    """Combine MCP config approval_class + impact score + PII findings."""

    # Check MCP config for explicit class
    server_config = config.MCP_SERVERS.get(server_id, {})
    tool_config = server_config.get("tools_config", {})
    explicit_class = tool_config.get(tool_name.split(".")[-1])

    # PII escalation
    has_blocking_pii = any(f.action == "block" for f in pii)
    has_flagged_pii = any(f.action == "flag" for f in pii)

    if has_blocking_pii:
        return ActionClass.EXTERNAL_CRITICAL

    if explicit_class:
        cls = ActionClass(explicit_class)
        # Escalate if impact is high
        if impact.score >= 8 and cls in (ActionClass.EXTERNAL_LOW, ActionClass.EXTERNAL_MEDIUM):
            return ActionClass.EXTERNAL_HIGH
        if impact.score >= 9.5:
            return ActionClass.EXTERNAL_CRITICAL
        return cls

    # No explicit config → use impact score
    if impact.score < 3:
        return ActionClass.INTERNAL
    elif impact.score < 5:
        return ActionClass.EXTERNAL_LOW
    elif impact.score < 7:
        return ActionClass.EXTERNAL_MEDIUM
    elif impact.score < 9:
        return ActionClass.EXTERNAL_HIGH
    else:
        return ActionClass.EXTERNAL_CRITICAL

            raise HTTPException(502, f"MCP server error: {r.text}")
        return r.json()
