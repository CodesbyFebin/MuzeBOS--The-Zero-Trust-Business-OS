# MeTaBos — 500 Self-Evolving AI Employees (Blueprint Section 15)

**Open-source, self-hosted, MCP-connected, human-approved. Each employee lives in its own sandbox, learns from peers, and evolves to mastery.**

---

## 15.1 Design Principles

| Principle | Implementation |
|-----------|---------------|
| **Open-source only** | Every agent is a Llama 4 Scout/Maverick instance running on the shared vLLM pool. No proprietary model calls. |
| **Self-evolving** | Each agent has a **Skill Memory** (persistent, per-role) that grows via: (a) task completion reflection, (b) peer skill transfer, (c) observer critique feedback. Inspired by Hermes Agent's learning loop + OpenSkill's open-world skill acquisition. |
| **Dedicated sandbox** | 1 agent = 1 `Sandbox` CRD. No sharing. Full isolation. |
| **MCP-native** | Every agent connects to the outside world exclusively via **MCP servers** (15,930+ public servers available). No custom glue code. |
| **Human approval gate** | **ALL outgoing actions** (external API calls, emails, payments, deployments, legal filings) require owner approval via the Next.js console before execution. Internal actions (memory writes, internal queries, skill updates) are autonomous below impact threshold. |
| **Peer learning** | Agents in the same swarm share a **Skill Exchange** (Qdrant collection per swarm). When Agent A masters a sub-task, its skill is published. Agent B in the same role can pull it. |
| **Mastery progression** | Each agent has a **Skill Level** (1–10) per sub-capability. Level advances only when: (a) task success rate >90% over 50 tasks, (b) Observer Agent validates no drift, (c) skill is peer-reviewed by 2+ same-role agents. |

## 15.4 MCP Architecture (Central Gateway)

**~15,930 public MCP servers** available (official registry: `registry.modelcontextprotocol.io`). MeTaBos uses a **central MCP Gateway** (self-hosted) that all 500 agents connect through.

### Why a Gateway (not direct connections)

| Concern | Solution |
|---------|----------|
| Auth | Gateway holds OAuth2/OIDC tokens; agents get scoped, per-task, expiring credentials |
| Approval gate | **ALL outgoing MCP calls pass through the gateway → approval check → execute or reject** |
| Audit | Every tool call logged with agent ID, timestamp, parameters, result |
| Rate limiting | Per-agent, per-swarm, per-tool quotas |
| FOSS policy | Gateway enforces: no data-sharing, no hosted-service dependency without declaration |
| Discovery | Agents query the gateway for available tools matching their role |

### MCP Gateway Deployment (in control-plane namespace)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mcp-gateway
  namespace: control-plane
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: gateway
        image: metabos/mcp-gateway:1.0
        ports:
        - containerPort: 9000   # MCP Streamable HTTP
        - containerPort: 9001   # Admin/audit API
        env:
        - name: APPROVAL_ENDPOINT
          value: "http://fastapi.control-plane.svc:8443/api/approvals"
        - name: AUDIT_DB
          value: "postgresql://metabos:***@postgres.control-plane.svc:5432/audit"
        - name: REGISTRY_URL
          value: "https://registry.modelcontextprotocol.io/v0"
        resources:
          requests: {cpu: "2", memory: "4Gi"}
          limits: {cpu: "4", memory: "8Gi"}
---
apiVersion: v1
kind: Service
metadata:
  name: mcp-gateway
  namespace: control-plane
spec:
  selector:
    app: mcp-gateway
  ports:
  - name: mcp
    port: 9000
    targetPort: 9000
  - name: admin
    port: 9001
    targetPort: 9001
```

### Agent → MCP Call Flow (with approval)

```
Agent (sandbox)
    │
    │  MCP request: "send email to client@x.com"
    ▼
MCP Gateway (control-plane)
    │
    ├── 1. Auth check (scoped token valid?)
    ├── 2. Policy check (OPA: is this tool allowed for this role?)
    ├── 3. Classification: internal vs EXTERNAL
    │       │
    │       ├── INTERNAL (memory write, internal query) → EXECUTE
    │       │
    │       └── EXTERNAL (email, payment, deploy, legal)
    │               │
    │               ▼
    │         ┌─────────────────────────────┐
    │         │  APPROVAL GATE              │
    │         │  - Create approval record   │
    │         │  - Notify owner (console +  │
    │         │    Telegram + email)        │
    │         │  - TTL: 30 min (expires)    │
    │         │  - Replay protection        │
    │         └──────────────┬──────────────┘
    │                        │
    │              ┌─────────┴─────────┐
    │              ▼                   ▼
    │         APPROVED             REJECTED
    │         (owner clicks)       (or TTL expires)
    │              │                   │
    │              ▼                   ▼
    │         EXECUTE via         LOG + NOTIFY
    │         MCP server          agent: "blocked"
    │              │
    │              ▼
    └──────────────┘
         │
         ▼
    MCP Server (e.g., gmail-mcp, github-mcp, erpnext-mcp)
         │
         ▼
    External system
```

**Key rule: No agent can bypass the gateway. NetworkPolicy enforces: sandboxes can ONLY reach `mcp-gateway:9000` for external tool calls. Direct egress to external APIs is blocked.**

## 15.6 Human Approval (JEV Gate) — All Outgoing Actions

**"JEV" = Just-in-time External Validation.** Every action that touches the outside world requires owner approval.

### Approval Matrix

| Action Class | Examples | Approval | TTL |
|-------------|----------|----------|-----|
| **Internal** (autonomous) | Memory write, skill update, internal query, peer skill pull | None | — |
| **Internal-high** (logged, no gate) | Create new role, modify workflow, update KPI | Observer review (async) | — |
| **External-low** (auto-approve with log) | Read-only API call, fetch data, search | None (logged) | — |
| **External-medium** (owner approval) | Send email, create CRM record, post to social, schedule meeting | **JEV: owner clicks approve** | 30 min |
| **External-high** (owner + Observer) | Send payment, sign contract, deploy to prod, file legal, terminate employee | **JEV: owner + Observer Agent both approve** | 15 min |
| **External-critical** (owner + 2-person) | >$10K spend, legal filing, data deletion, security credential change | **JEV: owner + second human (configurable)** | 10 min |

### Approval Record Schema (PostgreSQL)

```sql
CREATE TABLE approvals (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    agent_id      UUID NOT NULL,          -- which sandbox requested
    swarm_id      TEXT NOT NULL,
    action_class  TEXT NOT NULL,          -- internal / external-low / medium / high / critical
    tool_name     TEXT NOT NULL,          -- MCP tool (e.g., "gmail.send")
    parameters    JSONB NOT NULL,         -- full tool call params
    impact_score  NUMERIC(2,1) NOT NULL,  -- 0-10
    status        TEXT DEFAULT 'pending', -- pending / approved / rejected / expired
    approved_by   UUID,                   -- owner JWT sub
    observer_ok   BOOLEAN,                -- Observer Agent validated
    created_at    TIMESTAMPTZ DEFAULT now(),
    expires_at    TIMESTAMPTZ NOT NULL,   -- TTL from action_class
    resolved_at   TIMESTAMPTZ,
    audit_hash    TEXT NOT NULL           -- hash chain: H(prev_hash || this_record)
);
```

## 15.7 Peer Learning & Skill Exchange

### Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│  Skill Exchange (per swarm, Qdrant collection)                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  swarm-01-skills (Qdrant collection)                             │
│  ├── skill: code-review-security-scan (agent-007, level 7)      │
│  ├── skill: ci-pipeline-debug (agent-003, level 8)              │
│  ├── skill: k8s-deploy-rollback (agent-012, level 6)            │
│  ├── skill: incident-postmortem (agent-019, level 9)            │
│  └── ... (grows over time)                                      │
│                                                                  │
│  Access: read-only for all agents in swarm-01                    │
│  Write: only the agent that created the skill                    │
│  Validation: Observer Agent + 2 peer agents before publish       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Cross-Swarm Learning (controlled)

| Mechanism | How |
|-----------|-----|
| **Swarm-to-swarm** | COA identifies a skill in Swarm 01 that would benefit Swarm 05. Creates a "skill transfer" approval. Owner approves. Skill is copied to Swarm 05's collection with attribution. |
| **Role-specific global** | All "AI Bookkeeper" agents across all swarms share a `global-finance-skills` collection. When one masters a new reconciliation pattern, all benefit. |
| **Failure sharing** | When an agent fails, the failure mode is published (anonymized) to the swarm's `failure-modes` collection. Other agents learn what NOT to do. |

### Mastery Progression

```
Level 1:  New agent. Base skill from role template. 0 tasks done.
Level 2:  10 tasks completed, >70% success.
Level 3:  25 tasks, >80% success. First peer skill pulled.
Level 4:  50 tasks, >85% success. Observer validated.
Level 5:  100 tasks, >88% success. Can teach (skill published).
Level 6:  200 tasks, >90% success. Handles edge cases.
Level 7:  350 tasks, >92% success. Peer-reviewed by 3+ agents.
Level 8:  500 tasks, >94% success. Observer: "mastery confirmed."
Level 9:  750 tasks, >96% success. Creates new sub-skills.
Level 10: 1000+ tasks, >97% success. "Master." Can mentor new agents.
```

**Level gates are enforced by the COA.** An agent at Level 3 cannot be assigned Level 7 tasks. The COA routes by mastery level.

## 15.9 Sandbox Configuration (per agent)

Each of the 500 agents gets its **own dedicated sandbox** (not shared). The 5 `SandboxTemplate` profiles per swarm determine the *execution shape*; the agent identity is injected at claim time.

### Per-Agent Persistent Storage

```yaml
# Each sandbox has 3 volumes:
volumeClaimTemplates:
- name: workspace          # Task files, code, temp (1 GiB)
- name: skill-memory       # Persistent skill files (512 Mi, NEVER deleted)
- name: trajectories       # Last 100 task traces (256 Mi, rolling)
```

**`skill-memory` is the key volume.** It persists across sandbox restarts. When an agent is released and re-claimed, its skills are intact. This is what makes "self-evolving" real — the agent doesn't reset.

### NetworkPolicy (per sandbox — strict)

```yaml
egress:
# 1. vLLM inference (LLM calls)
- to:
  - namespaceSelector: {matchLabels: {name: inference}}
  ports: [{protocol: TCP, port: 8000}]

# 2. MCP Gateway (ALL external tool calls go through here)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 9000}]   # MCP Gateway

# 3. Control plane API (task state, approvals, memory)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 8443}]   # FastAPI

# 4. Qdrant (skill exchange, retrieval memory)
- to:
  - namespaceSelector: {matchLabels: {name: control-plane}}
  ports: [{protocol: TCP, port: 6333}]

# NO direct external egress. Period.
# All external calls MUST go through MCP Gateway → approval → execute.
```

**This is the critical security property:** an agent in a sandbox **cannot** make a direct HTTP call to Gmail, GitHub, or any external API. It MUST go through the MCP Gateway, which enforces the JEV approval gate.
